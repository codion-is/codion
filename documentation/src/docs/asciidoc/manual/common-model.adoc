== File Preferences

{url-javadoc}{common-model}/is/codion/common/model/preferences/FilePreferences.html#filePreferences(java.lang.String)[FilePreferences.filePreferences(String)] provides a file-based implementation of the Java Preferences API that removes the restrictive length limitations of the default implementation.

=== Motivation

The default Java Preferences API imposes the following restrictions:

* Maximum key length: 80 characters
* Maximum value length: 8,192 characters (8 KB)
* Maximum node name length: 80 characters

These limits can be problematic when storing configuration data such as serialized table column preferences or other structured data that may exceed these limits.

=== File Storage

Preferences are stored in a JSON file at a platform-specific location:

* **Windows**: `%LOCALAPPDATA%\Codion\\{filename}.json`
* **macOS**: `~/Library/Preferences/Codion/{filename}.json`
* **Linux**: `~/.config/codion/{filename}.json` (follows XDG Base Directory specification)
* **Other**: `~/.codion/{filename}.json`

NOTE: The global preferences file location can also be specified via {url-javadoc}{common-model}/is/codion/common/model/preferences/FilePreferences.html#PREFERENCES_LOCATION[FilePreferences.PREFERENCES_LOCATION] if these default locations do not fit your use-case.

The file is written in UTF-8, in the following JSON format:

[source,json]
----
{
  "normal.key": "normal value",
  "a.key.far.longer.than.the.eighty.characters.the.standard.implementation.allows.for.a.key": "a value of any length",
  "key.with.newlines": "Line 1\nLine 2\nLine 3",
  "columns": {
    "name": {
      "w": 120,
      "i": 0
    },
    "email": {
      "w": 200,
      "i": 1
    }
  },
  "not.json": "[a, b]"
}
----

A value is read back as it was put. One that is JSON as a JSON library writes it, such as serialized column preferences, is stored as a nested JSON structure, keeping the file readable, any other text as a string. There is one exception: a value that is an empty JSON object, `{}`, is not written to the file, nor is a node holding no values.

=== Features

* **No length restrictions** - Keys, values and node names can be of any length
* **JSON format** - Human-readable and easily editable
* **Thread-safe** - Safe for concurrent access within a single JVM
* **Multi-JVM safe** - File locking ensures safe concurrent access from multiple JVMs
* **Atomic writes** - Changes are written atomically to prevent corruption
* **Standard API** - Uses the standard Java Preferences API, see <<_differences_from_the_standard_implementation, the differences>> below
* **Full hierarchy support** - Create nested preference nodes with paths

The hierarchical structure is stored as nested JSON objects, each node marked with `.node`, which tells it from a JSON value. This is the file before the `database` node is removed:

[source,json]
----
{
  "myapp": {
    ".node": true,
    "ui": {
      ".node": true,
      "theme": "dark",
      "font.size": "14"
    },
    "database": {
      ".node": true,
      "connection.url": "jdbc:postgresql://localhost/mydb",
      "connection.pool.size": "10"
    }
  }
}
----

=== Differences from the standard implementation

* A key and a child node can not share a name, both being members of the same JSON object. Putting a value for a key naming a child node throws `IllegalStateException`, as does putting a value into a child node named after a key.
* A `PreferenceChangeListener` is not notified when a value is put.
* `flush()` and `sync()` do the same: reload the file if it has been modified, re-apply the changes not yet saved and save them, once for the whole tree, leaving the file untouched when there are no changes.

=== Concurrency and Multi-JVM Access

The file preferences implementation is designed to be safe for concurrent access:

* **Within a single JVM**: All operations are synchronized using internal locks
* **Across multiple JVMs**: A file lock is held from the reload to the write, so that two instances saving at the same moment both keep their changes
* **Atomic writes**: Changes are written to a temporary file and atomically moved, a process ending while saving leaves the file as it was
* **External changes**: `flush()` and `sync()` reload the file if another instance has modified it and re-apply the changes not yet saved on top of it. Where the two disagree on a name, one using it for a key and the other for a node, what is saved in the file stays and the change is left out

=== Corrupted files

A file that is not valid JSON is copied to `{filename}.json.corrupt.{timestamp}` and replaced the next time the preferences are saved. Found at startup the preferences start out empty, found later, the file having been read before, the preferences held are kept and written back.
